**Reconfirmado em 13/08/2026 com insert real via PostgREST (service role) contra o Supabase ao vivo.** `UN`, `CX` e `DZ` passam; `FD` (Fardo) retorna `23514 — new row for relation "cotacao_itens" violates check constraint "cotacao_itens_tipo_unidade_check"`. A migration que adiciona `FD` à constraint (`supabase/migrations/005_allow_fd_unit_type.sql`) existe no repo mas **nunca foi rodada no banco real** (mesmo padrão de divergência migration-vs-produção descrito mais abaixo). Sem acesso a DDL por aqui — só leitura/escrita via PostgREST.

**Isso deixou de bloquear a publicação.** `backend/src/cotacoes/unit.util.ts` + `criarCotacao` (`cotacoes.service.ts`) tratam o caso: `cotacao_itens.unidade` **não tem constraint nenhuma** (confirmado ao vivo), então ela guarda a unidade real; quando o insert volta com 23514 em `tipo_unidade`, o backend regrava só essa coluna com um valor aceito (`toLegacySafeUnit`) e as leituras resolvem a unidade verdadeira a partir de `unidade` (`resolveUnit`, aplicado em `detalhe` e `atualizarItem`). O comportamento **se auto-corrige**: assim que 005 rodar, o primeiro insert passa e o fallback deixa de ser exercitado, sem mudança de código.

**Ainda vale rodar `supabase/migrations/005_allow_fd_unit_type.sql` no SQL Editor do Supabase** para voltar a gravar `tipo_unidade` corretamente (hoje um item "Fardo" fica `unidade='FD'` / `tipo_unidade='UN'` no banco, e só a API devolve `FD` nos dois).

## O que é o projeto

VendaMais é uma plataforma B2B de e-procurement (cotação de preços) em português. Duas personas:

- **Empresário** — dono/gestor de loja/empresa. Monta cotações (RFQs) a partir do catálogo de produtos, convida fornecedores, compara propostas recebidas e aceita a vencedora.
- **Fornecedor** — responde cotações com preços por item, prazos e observações, e acompanha suas propostas.

Ver `analysis_results.md` (fluxo de negócio detalhado, com diagrama mermaid) e `markdown/config-atual-supabase.md` (dicionário de dados Supabase) — ambos na raiz do repo. Este CLAUDE.md resume e referencia os dois em vez de duplicá-los; leia-os quando precisar de detalhe de schema ou de produto.

## Stack técnica

- **Next.js 16** (App Router) + **React 19** + **TypeScript** (strict, path alias `@/*` → `./src/*`)
- **Supabase**: Postgres + Auth + Storage. Sem Prisma/Drizzle — queries via `@supabase/supabase-js`/`@supabase/ssr` direto. Tipos de banco são **mantidos à mão** em `src/lib/types/database.ts` (não gerados via `supabase gen types` — atualize manualmente ao mudar o schema).
- **Tailwind CSS 4** (config via CSS em `src/app/globals.css`, sem `tailwind.config.*`), Radix UI primitives, `class-variance-authority`, `lucide-react`, `framer-motion`, `sonner` (toasts).
- **Forms/validação**: `react-hook-form` + `@hookform/resolvers` + **Zod**. Uso de Zod é inconsistente hoje (ver "Padrões" abaixo).
- **Outras libs de domínio**: `@dnd-kit/*` (drag-and-drop), `@zxing/browser`+`@zxing/library` (scanner de código de barras no catálogo de produtos), `date-fns`.
- Sem Redux/Zustand — estado vem de Server Components + Server Actions + hooks locais.
- Sem Prisma — SQL bruto/migrations manuais (ver seção de banco abaixo).

## Modelo de dados e multi-tenancy

Ver `markdown/config-atual-supabase.md` para o dicionário completo. Resumo essencial:

- **RLS ativo em todas as tabelas.** Nunca assuma que dar `select *` no client é seguro só porque "funcionou local" — teste com um usuário de baixo privilégio.
- **Três eixos de papel, não um só**: `profiles.global_role` (`super_admin`/`user`), `memberships.role` (`owner`/`admin`/`member`/`vendedor`, por organização), e `profiles.tipo` (`empresario`/`fornecedor`). Combine os três ao decidir uma permissão nova — usar só um é o tipo de bug que já apareceu no histórico do projeto (ver gotchas de `sql/`).
- **Tenant ativo**: `profiles.active_organization_id` aponta a organização corrente do usuário. Sempre resolva isso antes de consultar produtos/categorias/cotações escopados por organização.
- **Redundância conhecida**: `products.category` (texto solto) duplica a relação formal `product_categories` — prefira a relação formal em código novo.
- Cadeia central: `cotacoes` → `cotacao_itens` / `fornecedores_convidados` → `propostas` → `proposta_itens`.

## Fluxo de negócio: cotação → proposta

Estados da cotação (`CotacaoStatus` em `src/lib/constants.ts`): `rascunho` → `aberta` → `em_andamento` → `encerrada`.
Estados da proposta (`PROPOSTA_STATUS_LABELS`): `enviada`/`recebida` → `aceita`/`recusada`.

1. `criarCotacao` (`src/actions/cotacoes.ts`) — cria a cotação (`rascunho`, ou `aberta` se `publish=true`) + insere `cotacao_itens`. **Não é transacional**: se o insert dos itens falhar, o código tenta compensar deletando a cotação recém-criada, mas não checa o erro desse delete.
2. `publicarCotacao` — transição `rascunho`→`aberta`, com **trava otimista** (`.eq('status','rascunho')` no update). Este é o padrão certo a copiar para outras transições de status.
3. Fornecedor chama `enviarProposta` (`src/actions/propostas.ts`) — só aceito se a cotação está `aberta`/`em_andamento`. O `valor_total` é calculado com a **quantidade solicitada pelo comprador**, não a do fornecedor (`quantidade_disponivel` é só informativo).
4. Empresário chama `gerenciarProposta(id, 'aceita')` — aceita a proposta, rejeita as demais (`status in (enviada, recebida)`) e fecha a cotação (`encerrada`) em uma sequência de updates separados (ver gotcha #2 — sem trava otimista aqui).

Ações não relacionadas mas parecidas pelo nome: `product-quotes.ts` é uma ferramenta de admin/moderador para registrar cotações de referência de produto — não faz parte do ciclo cotação/proposta.

## Padrões de código a seguir

- Toda Server Action fica em `src/actions/*.ts` e começa com `'use server'`.
- Guards de autorização (RBAC) ficam em `src/lib/authorization.ts` — nunca inline dentro da action. Padrão: `assert*` lança `Error` com mensagem amigável; a action captura e retorna `{ error: string }`.
- Ao adicionar lógica de permissão nova, separe a decisão pura (testável sem mock) de qualquer I/O, como em `roles.ts`/`roles.server.ts`.
- Validação com **Zod** é o padrão em `invitations.ts`/`admin-users.ts`/`invitation-accept.ts` — replique esse padrão em código novo. Hoje há inconsistência (`auth.ts` valida campos de `FormData` manualmente); não é preciso migrar retroativamente, mas Zod é a escolha para tudo novo.
- Invalidação de cache via `revalidatePath()` logo após cada mutação — ao adicionar uma nova transição de status, revalide os mesmos paths que as transições irmãs já revalidam (ver gotcha #4, onde isso já ficou inconsistente).
- Nomenclatura de domínio é em português (`cotacao`, `proposta`, `fornecedor`, `empresario`) — mantenha esse idioma para símbolos de domínio; comentários/strings de UI também em pt-BR.

## O que NÃO fazer

- Não usar `git commit --no-verify` ou pular hooks.
- Não editar uma migration já aplicada em `supabase/migrations/` — criar uma nova numerada.
- Não instanciar o client Supabase com `SUPABASE_SERVICE_ROLE_KEY` fora de Server Actions/rotas server-only (nunca no client/browser).
- Não escrever em `products`/`product_quotes` com o client logado — a RLS legada descarta a escrita em silêncio (ver gotcha #21). Use `requireProductAccessContext()` e feche com `.select()`.
- Não fazer `DROP TABLE`/recriar a tabela `profiles` (ver gotcha #12).
- Não hardcodar a margem (28,5%) nem cor de colocação/tendência em componente — leia a config (`getMargemConfig`) e use os tokens `rank-*`/`trend-*` (ver gotchas #30/#31).
- Não usar `showToast` (`@/components/ui/toast`) sem confirmar que a página monta `<ToastContainer/>` — senão o aviso some em silêncio (ver gotcha #36). Em código novo, `toast` do sonner.
- Não pôr tooltip em célula do corpo da tabela de comparação — a explicação vai no cabeçalho da coluna (ver gotcha #39).
- Não pedir e-mail em tela de auth, nem exibir `users.email` cru — pode ser o sintético (`@phone.vendamais.local`). Use `emailExibivel`/`identificadorExibivel` de `src/lib/phone.ts` (ver alerta no topo e gotcha #41).
- Não chamar `supabase.auth.signInWithPassword`/`auth.admin.createUser` fora de `src/lib/auth/phone-auth.ts` — é lá que o telefone vira e-mail e que a conta legada é resolvida.
- Não montar URL de proposta à mão: use `propostaPath`/`propostaUrl` (`src/lib/routes.ts`), slug `/proposta/` no singular (ver gotcha #42).
- Não apontar `<img>` direto pra `public/logos/` — use `<Logo>` de `src/components/brand/logo.tsx`. Em superfície de fundo escuro fixo (não segue o tema), passe `textClassName="text-white!"` (ver gotcha #44).

- Não passar classe de `display` (`hidden`, `block`, `flex`...) no `className` do `Tooltip` — ele já tem `inline-flex` fixo e `cn()` aqui não faz merge; envolva com outro elemento (ver gotcha #48).
- Não commitar sem rodar `npm run lint`.
